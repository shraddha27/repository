# Unfinished work and operational risks

The following items remain deliberately incomplete or require validation before production. The assessment prioritizes explaining these gaps over claiming guarantees the external APIs do not provide.

| Priority | Item | Proposed next step and validation | Why incomplete / decision | Risk |
|---|---|---|---|---|
| P0 | Define the WMS duplicate/idempotency contract | Agree on an idempotency key and retention window, or provide a lookup/reconciliation API. Test lost-response, post-commit 5xx, and replay scenarios against the WMS. | The supplied API has no idempotency or status lookup contract; silently retrying a POST could duplicate side effects. Automatic replay of ambiguous batches is deliberately disabled. | Runs can require manual reconciliation and remain blocked; exactly-once behavior cannot be guaranteed by this client alone. |
| P0 | Validate the four-hour completion window at 10 million records | Benchmark the deployed producer, SQS queue, independent ECS worker service, distributed rate limiter, and checkpoint path with realistic PIM/WMS latency and failures. Tune the minimum, maximum, and backlog target only from measurements. | Current rate limits and batch sizes give an ideal sequential lower bound of about 1 hour 57 minutes for 10 million products; the queued task timeout is set to four hours. A local synthetic 1M-record run completed in 10.4 minutes using four local threads, an immediate deterministic HTTP stub, the 20-requests/second limiter, and SQLite checkpoints; it excluded PIM, S3, SQS, DynamoDB, and ECS autoscaling. A prior LocalStack SQS/DynamoDB attempt did not complete and did not exercise Fargate. | The four-hour setting is not a completion guarantee. Real API latency, queue dispatch, distributed limiter/checkpoint costs, scaling delay, and retries may cause the task to exceed it. The former 30-minute target is impossible under the current API caps. |
| P1 | Production deployment and infrastructure validation | Build/publish an immutable image, configure VPC/NAT and secret ARNs, run `terraform init/validate/plan` in a configured AWS account, and exercise the scheduled producer, ECS worker service, queue, rate limiter, and alarms. | This environment has no AWS account, image registry, credentials, or deployed network to validate real service integration. Terraform is a reviewed starting point, not an applied deployment. | Invalid account-specific configuration, permissions, connectivity, or service quotas could block deployment. |
| P1 | Tune autoscaling and idle-cost policy | Measure queue depth and WMS latency in AWS, tune `worker_desired_count`, `worker_max_capacity`, and `worker_target_backlog_per_task`, and compare ECS service cost with an SQS-triggered Lambda worker if batches are short-lived. | Queue-backlog-based ECS Application Auto Scaling is configured, but has not been validated in AWS or tuned against production traffic. The service retains its minimum number of workers between runs. | A high minimum can waste compute when idle; a low maximum or poorly tuned backlog target can underuse the WMS request allowance or add cost without improving throughput. |
| P1 | Resume/reconciliation operator tooling | Add an authenticated command or runbook that inspects an ambiguous batch, records an operator-approved outcome, resumes the run, and clears a stale global lock only after reconciliation evidence. Test crash windows and interrupted DynamoDB writes. | Automatic force-retry would violate the duplicate requirement. The current implementation blocks ambiguous runs and retains the global lock but does not provide a UI or a guarded resolution workflow. | Manual database edits are error-prone; a stale lock blocks future runs, and unsafe cleanup could allow duplicate processing. |
| P1 | Consistent PIM snapshot semantics | Confirm whether pagination is snapshot-consistent. If not, request a PIM snapshot token/change feed and test concurrent catalogue changes during a run. | The provided API exposes page/next-page only and cannot express a snapshot/version boundary. | Inserts or deletes while pages are being read can result in omissions or duplicate source rows. |
| P1 | Complete operational metrics and alert thresholds | Add page latency, retry, rejected/ambiguous outcome, and whole-run metrics, then define alert thresholds with Operations. Validate the worker dashboard and EMF extraction in AWS. | Worker WMS attempt latency/count/error metrics and a dashboard for WMS rate, queue backlog, and running workers are configured; they have not been validated in AWS. Page and run metrics and operating thresholds remain to be agreed. | Diagnosis and SLA alerting may be slower or less informative than desired. |
| P2 | Automated lifecycle/checkpoint retention policy | Agree on run-state retention, then add DynamoDB TTL or an archival process and verify lifecycle behavior. S3 export expiry is configured at 90 days. | The assessment specifies 90-day S3 exports but not run-state retention; retaining state is currently safer for reconciliation. | DynamoDB storage grows with daily SKU outcomes until a retention policy is set. |
| P2 | Load, chaos, and AWS integration test coverage | Add tests with LocalStack or a dedicated test AWS account for S3, SQS, and DynamoDB, plus high-volume, global rate-limit, partial-response, duplicate delivery, and concurrent worker crash-injection tests. | Unit tests cover queue dispatch and local checkpoint paths, but the distributed services and ECS worker service have not been executed together in this environment. | Mocks cannot fully validate IAM, FIFO behavior, distributed limiter timing, AWS networking, task scaling, or service quotas. |
